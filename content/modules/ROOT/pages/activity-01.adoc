= Getting Started

== Overview

Here is a quick overview of the first activities in this lab:

- Log in to the Red Hat Automotive Suite with the lab user assigned to you.
- Open your personal, ready-to-code workspace in Red Hat OpenShift Dev Spaces, the cloud development environment of the Red Hat Automotive Suite.
- Verify that the Cloud Automotive Image Builder service (the RHAS Builder) is reachable from your workspace.
- Authenticate to the Jumpstarter service so you can lease a test device later.

Your user account has already been created for you. Every lab user gets a personal workspace in OpenShift Dev Spaces,
with the lab repository cloned into it. OpenShift Dev Spaces provides all supporting infrastructure, so that you can
focus on the lab, not on setup.

== Before you start

Some of the activities in this lab require you to perform certain actions in the various user interfaces or to type commands in a terminal window.
In order to highlight the different activities and their importance, we use the following conventions:

IMPORTANT: This is a step that is critical for the success of this lab.

NOTE: This is information that you should know, but it is not critical for the success of this lab.

TIP: This is a tip that will help you complete the lab.

Sections marked *Bonus* are not part of the core lab. Do them only if you have time left, during the lab or afterwards.

Some parts of the lab are shown by your instructors on the projector, such as a change running through the build
pipeline. They are marked as *Demonstration* and are not part of your hands-on steps.

[#devspaces]
== Open your workspace

Every lab user has a personal workspace, named `rhas-starter`. Depending on how far the lab environment was prepared for
you, it either exists already or you create it now. Look at the left side of the Dev Spaces dashboard:

* If `rhas-starter` is listed under *Recent Workspaces*, click the workspace name, or click the *⋮* menu next to it and choose *Open*.
* If the dashboard shows *Workspaces (0)* and no recent workspaces, create your workspace from the lab repository:
.. Click *Create Workspace* on the left.
.. Under *Import from Git*, paste the lab repository URL into the *Git repo URL* field:
+
[source,sh,role=copypaste,subs="+attributes"]
----
{lab_repo_url}
----
.. Click *Create & Open*.

The workspace now starts. It walks through initializing, waiting for the workspace to start, and finally opening the IDE.

image::starter/03-workspace-starting.png[]

NOTE: This takes about a minute on the shared lab cluster.

IMPORTANT: If prompted "Do you trust the authors of the files in this workspace?", click *Yes, I trust the authors*

TIP: On the bottom right of the screen you may see some popup notifications, you can safely dismiss them.

You should see a familiar *VS Code* development environment in your browser, with the lab repository `sc-demo` in the file explorer.

[TIP]
====
If your workspace does not start or behaves strangely, go back to the Dev Spaces dashboard and use the *⋮* menu next to the workspace:

* *Restart Workspace* restarts it and keeps your files.
* *Delete Workspace* removes it. To get a fresh one, create it again from the lab repository with *Import from Git*, as described above.
====


[#verify]
== Verify your environment

Before going further, confirm the workspace can reach the services it needs.

IMPORTANT: Select *Terminal -> New Terminal* from the menu at the top left, and confirm the prompt.

TIP: Enlarge the terminal panel so it fills the screen. You will spend most of this lab in it. If the editor asks you to
pick a color theme on first start, choose any.

Your prompt reads `(venv) sc-demo (main) $`. The Python virtual environment the lab needs is already active.

First, check that the Cloud Automotive Image Builder service is reachable:

[source,sh,role=execute]
----
caib status
----

You should see output like this:

[source,sh,subs="+attributes"]
----
Server  https://ado-build-api-automotive-dev-operator-system.{openshift_cluster_ingress_domain}
Source  CAIB_SERVER env
Status  reachable
----

image::starter/04-caib-status.png[]

NOTE: `caib` reads the server address from the `CAIB_SERVER` environment variable, which is already set in your workspace. If the status is anything other than `reachable`, stop and ask for help — nothing later in the lab will work.

Next, confirm which OpenShift user you are:

[source,sh,role=execute]
----
oc whoami
----

This must print your lab user. Your workspace inherits the OpenShift login, so there is no separate `oc login` step.


[#jumpstarter]
== Authenticate to Jumpstarter

The `jmp` command-line tool needs its own authentication, using a browser-based device flow.

IMPORTANT: Run the login command. Note the hyphen — this is `jmp-login`, not `jmp login`.

[source,sh,role=execute]
----
jmp-login
----

The command prints a URL and waits:

[source,sh,subs="+attributes"]
----
Fetching configuration from login.auto-jumpstarter.{openshift_cluster_ingress_domain}...
To sign in, open the following URL in your browser:

  https://keycloak-keycloak.{openshift_cluster_ingress_domain}/realms/openshift/device?user_code=XXXX-XXXX

Waiting for authentication...
----

IMPORTANT: Copy the URL with *Ctrl+Shift+C* and open it in a new browser tab.

TIP: In a terminal, plain Ctrl+C interrupts the running command instead of copying. Use Ctrl+Shift+C.

IMPORTANT: On the *Grant Access to jumpstarter-cli* page, click *Yes*.

image::starter/05-grant-jumpstarter.png[]

Back in the terminal, the command completes:

[source,sh,subs="+attributes"]
----
Waiting for authentication...
Set 'user35' as the default client.
Server saved: https://ado-build-api-automotive-dev-operator-system.{openshift_cluster_ingress_domain}
----

image::starter/06-jmp-login.png[]

The name in the `Set '...' as the default client` line is your own lab user.

Finally, list the test devices Jumpstarter can give you access to:

[source,sh,role=execute]
----
jmp get exporters
----

[source,sh]
----
NAME             LABELS
mock-exporter-0  🟢 device=mock,type=virtual
mock-exporter-1  🟢 device=mock,type=virtual
mock-exporter-2  🟢 device=mock,type=virtual
qemu-exporter-0  🟢 device=qemu,type=virtual
qemu-exporter-1  🟢 device=qemu,type=virtual
qemu-exporter-2  ❌ device=qemu,type=virtual
...
----

Each line is an *Exporter*, a test device made available through Jumpstarter. If this command lists Exporters, your
Jumpstarter login works.

- The `qemu-exporter-...` lines, labeled `device=qemu`, are the virtual QEMU devices you work with in this lab.
- The `mock-exporter-...` lines, labeled `device=mock`, are simulated devices for testing Jumpstarter itself. You can ignore them.
- The marker in front of the labels shows whether an Exporter is available (🟢) or not (❌), for example because it is offline.
