= Booting a RHIVOS Image

== Overview

In this activity, you take an operating system image that has already been built by the automated pipeline, and boot it on
a virtual device through Jumpstarter:

- Lease a virtual device from Jumpstarter
- Pick an image from the Cloud Automotive Image Builder
- Flash the image onto the device, power it on, and log in

Jumpstarter manages remote access to Exporters using *Leases*. A lease gives you exclusive access to an Exporter for a
specified period of time. When you request a lease, the Jumpstarter Service finds a free Exporter that matches a label selector.
Once the lease is granted, you work with the device in a session, just as if it were connected to your machine.

Not only can Jumpstarter help automate hardware testing in CI pipelines, but as your project grows,
Jumpstarter's remote access capabilities let you share limited hardware devices across
geographically dispersed teams in a secure, controlled, and efficient manner.

NOTE: In this lab, everybody gets a virtual QEMU device. The same commands work with a physical board connected to an Exporter.


[#lease]
== Lease a virtual device

To lease a QEMU Exporter and open a session on it, run the following command in your terminal:

[source,sh,role=execute]
----
jmp shell -l device=qemu
----

The `-l` parameter selects an Exporter by label. Every Exporter in this lab carries the labels
`device=qemu,type=virtual`, so `device=qemu` matches any free one.

The lease is granted for 30 minutes, and is released automatically when you leave the shell.
You keep using this lease in the next activity, so move on without long breaks.

IMPORTANT: After 30 minutes, the lease ends and the Jumpstarter shell closes by itself, even in the middle of your work.
You are then back at the `(venv) sc-demo (main) $` prompt. This is expected: lease a device again, and flash and boot
the image as described below. It only takes a minute. Set `DISKIMAGE` again before you flash: the variable is lost
together with the old shell.

TIP: Notice that your shell prompt changed to `sc-demo ⚡qemu-exporter-0 ➤`, naming the Exporter you were given. This is to remind you that you are inside a Jumpstarter shell session.

NOTE: While you hold a lease, the shell periodically prints `Token expires in ... Will attempt auto-refresh.` This is expected and can be ignored.

To see the hardware interfaces of the Exporter you have leased, run the `j` command without parameters:

[source,sh,role=execute]
----
j
----

You should see an output like this:

[source,sh]
----
Usage: j [OPTIONS] COMMAND [ARGS]...

  Generic composite device

Options:
  --help  Show this message and exit.

Commands:
  console  Serial port client
  flasher  Generic flasher interface
  power    Generic power
  qemu     Generic composite device
----

As the Exporter is connected to a virtual QEMU device, you can use these subcommands to interact with it:

- flash a new image with `flasher`
- control the power with `power`
- access the serial console with `console`

A physical device with a similar interface is used in exactly the same way.


[#caibimagelist]
== Pick an image

Images are built by the Cloud Automotive Image Builder service (the RHAS Builder) and kept in the cluster registry, the *artifact store*.
List them:

[source,sh,role=execute]
----
caib image list
----

This lists every image the build service has produced, with its status, age, the service account that
built it, and the registry URI.

The image names are generated by the pipeline and look cryptic, for example `pr-build-validate-mjvmb-57433`.
You do not need to type them: you copy the URI instead.

IMPORTANT: Copy the URI of the most recent image whose name starts with `pr-build-validate` and whose status is `Completed`.
Skip images with any other status, and images with other names. It looks like this:

[source,sh,subs="+attributes"]
----
default-route-openshift-image-registry.{openshift_cluster_ingress_domain}/automotive-dev-operator-system/pr-build-validate-<id>:disk
----

TIP: Select the URI with the mouse and copy it with *Ctrl+Shift+C*.

NOTE: The subcommand is `image`, singular. `caib images list` is not a valid command.


[#flash]
== Flash and boot the device

First store the image URI in a variable, pasting the URI you copied:

[source,sh]
----
DISKIMAGE=<paste the URI here>
----

TIP: Type `DISKIMAGE=` yourself and paste the URI directly after the `=`, without spaces.

Then flash it onto your device:

[source,sh,role=execute]
----
j flasher flash oci://$DISKIMAGE
----

The image is pulled from the registry and streamed straight to the device — there is no intermediate file.
The compressed image is about 850 MB, and the whole operation takes only about 15 seconds.

The flash is finished when you see:

[source,sh]
----
Result: FLASH_COMPLETED
----

image::starter/08-image-list-lease.png[]

Now power on the device and attach to its serial console to watch it boot:

[source,sh,role=execute]
----
j power on && j console start-console
----

image::starter/09-flash-and-boot.png[]

NOTE: During boot you may see messages such as `ConvertPages: failed to find range` or `Initramfs unpacking failed: Decoding failed`. These are known cosmetic errors and do not affect the lab.

The system identifies itself as `Automotive Stream Distribution 10` (AutoSD, the upstream of RHIVOS) and shows the
login prompt `auto-app login:`. `auto-app` is the host name set in the image.
Log in with the following credentials:

.Username
[.no-copy-label]
[source,text,role=execute,subs=attributes+]
----
root
----

.Password
[.no-copy-label]
[source,text,role=execute,subs=attributes+]
----
password
----

TIP: Your shell prompt changes to `[root@auto-app ~]#`. This is to remind you that you are now on the serial console of the virtual device.

Check the system architecture:

[source,sh,role=execute]
----
uname -m
----

It prints `aarch64`: this is an ARM based device, just like most automotive ECUs. The same image can also be flashed onto a physical ARM board.

.Excursion: from the virtual device to a real board
****
Because the image is built for ARM, it is not limited to virtual machines. Your instructors will show the same kind of image
running on a Texas Instruments ARM SoC board, a platform close to what is used in vehicles today. With a board connected to a
Jumpstarter Exporter, leasing, flashing, and booting work exactly as you just did, only the Exporter label changes.

This excursion is a demonstration only. It is not part of your hands-on steps.
****

NOTE: This image is a classic, writable disk image (qcow2), not a read-only image-mode (bootc) image. Any change you make inside the running system is lost the next time you flash the device.
