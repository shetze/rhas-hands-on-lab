= How the Image Is Built

== Overview

The image you booted was not built by hand. It was produced by an automated pipeline on OpenShift, following the
xref:intro-rhas.adoc#rhivosworkflow[workflow from source code to the device]:

. A change is pushed to the lab repository.
. OpenShift Pipelines builds the application and packages it as an RPM.
. The Automotive Image Builder composes the RPM, the RHIVOS packages, and the application containers into an OS image, as described by the image manifest.
. Jumpstarter flashes the image onto a virtual device, and automated tests check that it boots and that the application works.

In this activity, you look at the two files in the lab repository that drive this process: the image manifest and the pipeline definition.
You only read them; you do not need to change anything.


[#manifest]
== The image manifest

The contents of the image are declared in a single file. Open `manifests/auto-app.aib.yml` in the editor.

The file is long, because it describes everything in the image, down to individual configuration files. You do not
need to read all of it. The following parts connect directly to what you saw on the device.

The `image` section at the top sets global properties:

[source,yaml]
----
image:
  hostname: auto-app
  selinux_mode: enforcing
----

This is where the host name in your prompt, `[root@auto-app ~]#`, comes from, and why `getenforce` printed `Enforcing`.

The `content` section describes the root partition. It lists the RPM repositories to pull from and the packages to install:

[source,yaml]
----
content:
  repos:
    - id: epel
      ...
      priority: 20
    - id: bigmachine
      baseurl: http://...
      priority: 10
    - id: local
      baseurl: file:///workspace/export/
      priority: 5
  rpms:
    - auto-app
    ...
    - podman
    ...
    - qm
    ...
    - tmux
    ...
    - auto-apps
    - auto-apps-selinux
    - dlt-daemon
    ...
    - selinux-policy-automotive
    - vsomeip3-routingmanager
    - vsomeip3-selinux
    ...
----

If a package is available from more than one repository, the repository with the lowest `priority` number wins.

Note the two similar names:

- `auto-app` is a small "Hello" program in the `src` directory of the lab repository. The pipeline builds it into an RPM
  and places it in `/workspace/export`, which the `local` repository points to. The automated boot test uses it to check
  that the image works.
- `auto-apps` is the demo application you explored: the engine service, the radio service, and the radio client. It is
  built separately and comes as a ready-made RPM from a demo package repository (`bigmachine`), together with
  `auto-apps-selinux`, the SELinux policy module for the demo.

`qm` installs the QM partition, and `selinux-policy-automotive` and `vsomeip3-selinux` add the SELinux policy for
automotive systems and for the SOME/IP communication.

The `container_images` entry pulls container images from a registry and embeds them in the image:

[source,yaml]
----
  container_images:
    - source: quay.io/shetze/auto-apps
      tag: latest
      name: localhost/auto-apps
      ...
    - source: quay.io/shetze/ffi_server-arm64
      tag: latest
      name: localhost/ffi_server
      ...
----

This is why you saw the image names `localhost/auto-apps` and `localhost/ffi_server` in `podman ps`: the containers are
already part of the OS image, so the device does not need network access to start its applications.

Each containerized application is started by a systemd *Quadlet* file, injected into the image through the `add_files` section.
This is the engine service you saw in the root partition:

[source,yaml]
----
  add_files:
    ...
    - path: /etc/containers/systemd/engine.container
      text: |
        [Unit]
        Description=engine service container (asil-to-qm)
        Requires=routingmanagerd.service
        After=routingmanagerd.service

        [Container]
        Image=localhost/auto-apps
        Network=none
        ...
        SecurityLabelType=ipc_t
        Exec=/usr/bin/engine-service
----

`SecurityLabelType=ipc_t` is where the SELinux label you saw with `ps axfZ` comes from. The permission to communicate
is declared right next to the application, in the image definition.

The `qm` section further down describes the QM partition in the same way. It sets the memory limit you hit with the
FFI client, and has its own packages, its own container images, and its own Quadlet files, such as `radio.container`
for the radio service:

[source,yaml]
----
qm:
  memory_limit:
    max: 20%
  content:
    ...
    container_images:
      ...
      - source: quay.io/shetze/ffi_client-arm64
        tag: latest
        name: localhost/ffi_client
      ...
    add_files:
      ...
      - path: /etc/containers/systemd/radio.container
        text: |
          [Unit]
          Description=radio service container (asil-to-qm)

          [Container]
          Image=localhost/auto-apps
          ...
          SecurityLabelType=qm_container_ipc_t
          ...
          Exec=/usr/bin/radio-service
----

The QM partition also installs the `auto-apps` RPM. This is the copy of the radio client you started outside the radio
container: the program is there, but without the `qm_container_ipc_t` label it may not use the communication sockets.

NOTE: Most file contents are written inline with `text:`. Larger files are kept next to the manifest in the
`manifests` directory and added with `source_path:`, for example the Quadlet files of the FFI client and server in
`manifests/systemd/`. RPMs that the pipeline builds, such as `auto-app`, must be placed in `/workspace/export`, where
the image builder finds them through the `local` repository.

Finally, the `auth` section sets the root password you used to log in.


[#pipeline]
== The build pipeline

The pipeline is defined as code in the repository, in `.tekton/pr-build-validate.yaml`. Open it in the editor.

https://pipelinesascode.com/[Pipelines as Code,window=_blank] connects the repository to the cluster: a webhook in the
Git repository notifies the cluster of every change. Every push to the `main` branch starts a new run of this pipeline,
named `pr-build-validate-<id>`. This is the name you saw in the image URI in `caib image list`.

The pipeline performs the following tasks:

- `setup-jmp`: Prepares a Jumpstarter client for the pipeline.
- `clone-repo`: Clones the repository at the commit that was pushed.
- `get-lease`: Requests a Jumpstarter lease on a virtual device (`type=virtual`, `device=qemu`) — the same kind of device you leased by hand.
- `setup-workspace`: Prepares a build workspace on the Automotive Image Builder service.
- `build-rpm`: Builds the `auto-app` RPM by running `make build-rpm-workspace`, which places it in `/workspace/export`.
- `build-os`: Builds the qcow2 image for the `qemu` target and the `arm64` architecture from `manifests/auto-app.aib.yml`, and stores it in the registry.
- `flash`: Flashes the new image to the leased device with `j flasher flash` — the same command you used.
- `validate`: Runs the tests in `tests/boot_test.py` against the running device.
- `cleanup`: Always runs at the end, releases the lease, and returns the device to the pool.

Open `tests/boot_test.py` to see what the `validate` task checks. The test powers on the device, logs in on the serial console
with the same credentials you used, and checks that the `auto-app` application prints `Hello from AutoSD!`:

[source,python]
----
class TestBootProcess(JumpstarterTest):
    selector = "type=qemu"

    def test_boot(self, client):
        client.power.on()
        with client.console.pexpect() as console:
            console.expect_exact("login:", timeout=60)
            console.sendline("root")
            ...

    def test_auto_app(self, client):
        with client.console.pexpect() as console:
            console.sendline("auto-app")
            console.expect_exact("Hello from AutoSD!", timeout=30)
----

The test uses the Jumpstarter Python API and https://docs.pytest.org/en/stable/[pytest,window=_blank]. The steps you performed by hand in the
previous activities, such as leasing, flashing, powering on, and logging in, are exactly what the pipeline does automatically for every change.

This is the point of the Red Hat Automotive Suite: every change is built into a complete OS image and tested on a device,
inside the normal development cycle. Today the device is a virtual QEMU machine. Swap the Exporter label, and the same
pipeline flashes and tests a physical ECU.

[#pipelinedemo]
== Demonstration: a change runs through the pipeline

NOTE: This part is shown by your instructors on the projector. You do not push changes yourself: everybody would need
their own repository and access token, and 50 pipeline runs at once would overload the shared lab cluster.

Your instructor makes a small change to the image manifest, for example the `priority` of the `local` repository, commits it,
and pushes it to the `main` branch. You see:

. The webhook notifies the cluster, and Pipelines as Code starts a new `pr-build-validate-<id>` run.
. The OpenShift console shows the run as a graph of the tasks you just read about: right after cloning the
  repository, it leases a virtual device and prepares the build workspace in parallel. Then it builds the RPM and the OS
  image, flashes the image onto the leased device, and runs the boot test. The device stays leased for the whole build.
. When the run is finished, the new image appears in the artifact store.

A complete run takes about 10 to 12 minutes, most of it for building the OS image. This is the turnaround time for a
full operating system image, built and tested on a device, for every single change.

[#followbuild]
=== Follow the build from your workspace

You can watch the image being built from your own terminal. While the pipeline runs, list the images:

[source,sh,role=execute]
----
caib image list
----

The new image appears at the top of the list with the status `Building`:

[source,sh]
----
NAME                            STATUS     NOTIFICATION  AGE  REQUESTED BY
pr-build-validate-wwtcd-12095   Building   -             2m   system:serviceaccount:buildspace-...:pipeline
pr-build-validate-mjvmb-57433   Completed  -             2h   system:serviceaccount:buildspace-...:pipeline
...
----

Follow the output of the Automotive Image Builder for this image, using its name from the list:

[source,sh]
----
caib image logs <name of the building image>
----

You see much more detail than in the pipeline view: every step of composing the operating system image. Some warnings
scroll by; they are known and do not affect the result. When the build is done, the log ends with `completed
successfully` and the status in `caib image list` changes to `Completed`. Press *Ctrl+C* if you want to stop following
the log earlier.

[#newimage]
=== Bonus: boot the new image

Once the pipeline run has finished, the new image is available to everybody. The newest `pr-build-validate` image with
the status `Completed` is the one your instructor just built. If you like, go back to
xref:activity-02.adoc#lease[Booting a RHIVOS image], and lease, flash, and boot it on your own virtual device, exactly as
before. Make sure you copy the URI of this new image, not the one you used before. The demo application behaves the
same, because the change only touched the build configuration.

TIP: The pipeline and all participants share the same pool of virtual devices. If `jmp shell` keeps waiting for a
lease, all devices are busy. Press *Ctrl+C* and try again in a few minutes.


[#bonus]
== Bonus: build the application yourself

NOTE: This section is a bonus. Do it if you have time left.

The `auto-app` application can also be built directly in your workspace, without the pipeline. Your workspace already
contains the compiler and build tools.

Build the application:

[source,sh,role=execute]
----
make build-local
----

Then run it:

[source,sh,role=execute]
----
./bin/auto-app
----

[source,sh]
----
Hello from AutoSD!
Version: 0.1 (a571ff2)
----

This is the same program the `validate` task runs on the device. A cloud workspace like this one gives every developer
the same, ready-to-use build environment, without installing a toolchain on their own laptop.
